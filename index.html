02Our remit

What the Docs team owns

Since v1.36, Release Notes folded into Docs. That means we ship two things at once.

Documentation

  • Find every enhancement that needs docs, and track it to merged
  • Keep dev-1.38 healthy and in sync with main
  • Review docs PRs for quality, and get technical accuracy from the owning SIG
  • Merge the docs and unfreeze the website on release day

Release notes

  • Generate notes for every alpha, beta and rc
  • Edit them to the style guide, all cycle, not at the end
  • Collect Known Issues and validate major themes with SIG leads
  • Land the Final Release Notes PR before the release is cut
The mantra is "hurry up and wait." Weeks 1–8 are light: half an hour to two hours a day. Weeks 12–16 are heavy: five-plus hours a week, and release day is a long one. Plan your other commitments around the back half, not the front.

Why the two interim passes. There's a four-week gap between beta.0 on 4 Nov and rc.0 on 3 Dec with no tag to cut against. A month of unreviewed notes would land at rc.0, ten days before the final PR has to merge. So we clean the accumulated draft on 13 and 20 Nov even with no tag to generate from.

Running it

  • Install krel and always use the latest build — it gets fixes every cycle.
  • Generate the bundle for the tag, then open a PR against kubernetes/sig-release.
  • Edit with krel release-notes --fix. It's session-based, so you can pause and resume. Edits are saved as map YAML files.
  • Always keep release-notes-draft.md and release-notes-draft.json in sync. The JSON drives tooling; drift between them is silent and painful.
  • Cross-check the note count against merges in k/k since the previous tag — krel can skip PRs during rc fast-forward syncs.

Style rules that cause the most churn

Do

  • Past tense, verb first: Added, Fixed, Promoted, Graduated
  • API kinds bare in PascalCase: ConfigMap, ResourceClaim, EndpointSlice
  • Backtick flags, fields, commands, components, metrics, feature gates, versions
  • Graduation phases in Start case: Alpha, Beta, GA, Stable
  • One change per bullet, capitalised, ending in a period

Don't

  • Backtick an API kind — that blocks possessive apostrophes
  • Backtick or quote a field value: "set imagePullPolicy to Always"
  • All-caps ALPHA / BETA
  • Put the period inside a closing quote — it goes outside
  • Use "we", "just", "simply", or Latin abbreviations

A note has to stand alone: a reader should understand the change without opening the PR. If one is too vague to do that, open the PR and rewrite it with the actual symptom.

07Walkthrough

Sending a Slack reminder, step by step

This is the page to reopen when R3 comes around. Four steps, and the fourth is the one people skip.

Step 1

Work out who to actually reach out to

screenshot — KEP issue with Assignees panel, /sig + cc @… lines, and other subteams' recent comments circled
  • Start with the Assignees panel on the KEP issue.
  • Check the /sig and cc @… lines in the enhancement description.
  • Then read the recent comments from other subteams — Enhancements and Comms. Who they're @-mentioning is the strongest signal for who's currently driving the KEP, which is often not the original author.

Start with Assignees. If they look stale, the people other subteams are @-mentioning are the ones actually working on it.

Step 2

Copy the template from our group chat

screenshot — pinned template message in the Docs Slack group, ⋮ → Copy message menu open
  • The outreach template is pinned in our group. Hover the message, then ⋮ → Copy message (or Ctrl/Cmd+C).
  • Only change the author handles and the KEP links. Leave the dates and wording alone.

Never retype the template. Copying the pinned one means every author gets identical wording and identical dates.

Step 3

New group → your buddy → the authors → send

screenshot — fresh Slack DM group with buddy + KEP authors added, template pasted, author replying "Ack, I will open a placeholder PR"
  • Start a new group DM. Add your pair buddy first — before the authors, so you can't forget.
  • Add the KEP authors and owners you identified in step 1.
  • Paste and send. One message per owner group, listing all of their KEPs — that's why slices are grouped by SIG and shared owner.

Buddy first, then the authors. If you forget the buddy, the thread dies the day you're offline.

Step 4

Close the loop

  • Update Docs Status on the board.
  • Log the date in Sheet 7, under the right R-column.
  • React ✅ on the pair-up thread once your whole slice is sent.

This is what turns outreach into a number we can report at burndown. Skip it and our status reports become guesswork.

08Branch sync

The weekly branch sync

Merge main into dev-1.38 every Friday. This is the task most likely to be quietly skipped, and the one that bites hardest on release day.

Use the script rather than the manual steps:

./branch-sync.sh 1.38 -u <your-github-user>from release-team/role-handbooks/docs/branch-sync-script/

The sequence, by hand

Run it manually your first two or three times. The script is faster, but you need to recognise what a sync gone wrong looks like before you let something else do it for you.

CommandWhy
git fetch upstream mainBoth refs current before you start
git fetch upstream dev-1.38
git checkout -b merged-main-dev-1.38-20260911 upstream/dev-1.38Branch from the target. Date it, or next Friday's branch collides with this one
git merge upstream/mainPulls main in. Stops here if there are conflicts
git log --oneline upstream/dev-1.38..HEADSanity check before pushing — see below
git push origin merged-main-dev-1.38-20260911To your fork

Then open the PR against kubernetes/website — and change the base to dev-1.38.

Two ways to get it wrong

Branching off main

The direction is main → dev-1.38. The dev branch receives. Branch off main instead and your PR proposes replacing the dev branch's contents with main — deleting every in-progress feature doc for 1.38.

Leaving the base as main

GitHub defaults the base to main. Leave it and you've opened a PR merging the whole dev branch into the live site — unreleased feature docs and all. Check the base before you hit create, every time.

The sanity check catches both. git log --oneline upstream/dev-1.38..HEAD should print one merge commit plus whatever came from main. Hundreds of commits, or a diff deleting feature docs, means you started from the wrong base — delete the branch and start again.

The Fridays

Sep 4Sep 11Sep 18Sep 25 Oct 2Oct 9Oct 16Oct 23Oct 30 Nov 6Nov 13Nov 20Wed Nov 25 Dec 4Dec 11Tue Dec 15

Two are moved: Nov 27 is the day after Thanksgiving, so that sync happens Wed 25 Nov. Tue 15 Dec is the final pre-release sync and I'll run that one.

When it conflicts

Conflicts are the normal pain point — a page updated on both main and the dev branch. The dev-branch change is almost always an in-progress feature doc, so preserve it and layer the main update on top where they don't clash. If a conflict isn't obvious, git merge --abort and ask in #release-docs before re-attempting. Verify the branch builds before pushing.

Report it every week. Branch health goes in our status update. One or two missed syncs is a yellow status; three or more is red. Say so — nobody is annoyed by a yellow, everyone is annoyed by a surprise.
09Reviewing

Reviewing a docs PR

SIG Docs has limited capacity, so we review actively. A PR needs both a technical /lgtm and a docs /approve to merge.

Mechanics — check every time

  • Targets dev-1.38
  • Has the v1.38 milestone (apply with /milestone if not)
  • No WIP / Draft commits, and no revert commits
  • The KEP is actually likely to land in v1.38
  • Has a technical /lgtm — if not, add the relevant sig/* labels to help find a reviewer

Content — in this order

  • Correct page content type: Concept, Task, or Tutorial
  • Renders properly: numbered lists, code blocks, note/caution shortcodes
  • Makes sense and is spelled right
  • Follows the style guide's best practices and patterns to avoid
Don't block a /lgtm on style nits. Most PR authors are not writers, and many are non-native English speakers. A missing comma or some passive voice should not hold up accurate content. Spend your review energy on correctness and completeness. If a style issue really bugs you, note it and open a follow-up PR.

For technical accuracy, go to the reviewers and approvers named in the KEP's kep.yaml, or the SIG owner. It's fine — expected, even — not to understand every technical component. Get a technical LGTM when you're unsure.

Need help? #sig-docs, and the weekly PR Wrangler is your best resource.

One trap. PRs against the dev branch can merge any time they meet the bar — but be careful not to merge a feature that might slip to the next release. You can add /hold to mark a PR that shouldn't merge until the matching code change has landed.

11Escalation

When a KEP goes quiet

There's a defined path. Work it in order, and start earlier than feels necessary.

  1. Comment on the PR and send a Slack DM to the KEP owner.
  2. Ping the SIG chairs and tech leads in #chairs-and-techleads.
  3. Join the SIG's regular meeting and raise it in person.
  4. Last resort — escalate to the Subproject leads and Release Lead. Reach out at least a week before you need it, not the day you need it.
Missing Docs Freeze isn't the end. Owners can file an exception request — ideally in advance if they know they'll miss, otherwise within 24 hours. Exceptions need at least one extra business day after technical review so SIG Docs OWNERS can approve. Tell people this before the deadline; a filed exception is far easier on everyone than a late scramble.
12Status

Reporting status

We report a colour every week. The most important thing to know: SIG Docs actively wants to hear yellow and red early.

GreenOn track. Placeholder or review percentages at or above target, branch sync current, notes PR merged on time.
YellowSomething needs attention or might miss. Below 80% at a checkpoint, one or two missed branch syncs, a notes PR late or blocked.
RedWill miss without help. Below 60% at a checkpoint, three or more missed syncs, or a SIG we can't get a response from.

The handbook's own wording: "SIG Docs prefers and welcomes a status of yellow or red on anything that needs attention, has the possibility to miss deadlines or target dates, or requires follow-up from feature authors and SIGs that you're not receiving."

What to bring to the meeting

Tracked KEPstotal · need docs · no docs needed · unknown
Docs PRsno PR · draft · ready for review · merged
Placeholder PRscount and % against our internal target and the official date
Branch syncup to date, or last synced, or N commits behind
Release notescurrent tag's PR — open, merged, or blocked
Needs attentionspecific KEPs and specific asks, or "none"

Be specific in the last row. "A few KEPs are slow" gets nothing; "SIG Storage KEP #1234 hasn't replied to three touches, can someone from the release team nudge the chairs" gets action.
