The branch sync, in four steps

1

Branch off dev-1.38

git checkout -b merged-main-dev-1.38-<date> upstream/dev-1.38 — off the dev branch, never off main.

2

Merge main in

git merge upstream/main. Conflicts are normal: keep the dev branch's feature doc, layer main on top.

3

Check before pushing

git log --oneline upstream/dev-1.38..HEAD — one merge commit plus main's. Hundreds means you used the wrong base.

4

PR with base dev-1.38

GitHub defaults the base to main. Change it. This is the step people miss.

One assignee, one reviewer, every tag

Generating the notes

Once per shell. The token is a classic PAT with one scope ticked, and the editor has to be one that blocks:

export GITHUB_TOKEN=$(gh auth token)   # PAT: repo → public_repo, nothing else
export EDITOR="code --wait"            # must block until you save and close
export PATH=$PATH:$(go env GOPATH)/bin

--fix is the interactive review. It only works alongside --create-draft-pr — and without it you regenerate a raw draft that drops every correction the team has already made:

krel release-notes --create-draft-pr --fix \
  --tag=v1.38.0-alpha.1 --fork=<your-gh-user> --nomock

Each note opens in your editor as a YAML map, and every edit you save writes a map file. If the editor doesn't block — plain code, or nano left unsaved — krel reads an empty file, logs "YAML mapfile is blank, ignoring", and your edit is gone with no error. Ctrl+C when you're through the queue or out of time; answer y to "continue from the last session?" next run and it skips what you've already done. Then, before you let it open the PR:

krel release-notes validate --path-to-release-notes ./maps
You need an SSH key on your GitHub account as well. krel pushes the draft branch to your fork over git@github.com — the token only covers the API and opening the PR. Without a key you get Permission denied (publickey) at the push step, after the whole gather has run. Check with ssh -T git@github.com.

Reporting status

Green

On track. Percentages at target, branch sync current, notes PR merged on time.

Yellow

Needs attention or might miss. Below 80% at a checkpoint, one or two missed syncs.

Red

Will miss without help. Below 60%, three-plus missed syncs, or a SIG that won't answer.

SIG Docs actively wants yellow and red early — it's in the handbook. Nobody is annoyed by a yellow in week 6. Everybody is annoyed by a surprise in week 13. And be specific: name the KEP and the ask, not "some things are slow".
